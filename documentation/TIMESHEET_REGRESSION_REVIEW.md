## Обнаруженные проблемы и исправления

### 1. Двойная авторизация старых маршрутов — исправлено [С]

`timeaccess.Authorize` сначала вызывал `Identity` через проверку `calendar:read`, затем заново валидировал фактическое действие. Один прежний Validate (два HTTP-запроса к auth) превратился в два Validate (четыре HTTP-запроса) даже для обычного сотрудника и полноценного администратора. Это увеличивало задержку и число точек отказа, хотя read-доступ в первом ответе не использовался.

Теперь автор и результат доступа берутся из одного ответа проверки конкретного действия/владельца. При отказе и только для чужого пользователя остаются дополнительные проверки manager permission и Members. Для подтверждения сразу проверяется отдельное `timesheet.all:approve`. Нет дополнительного требования иметь `calendar:read` для изменения или административного подтверждения. Непустой session user ID по-прежнему обязателен.

Файл: `internal/timeaccess/policy.go`.

### 2. Изменение старых ошибок и разбора тела — исправлено [С]

Новая Require-обёртка проверяла тело до отсутствующей cookie и заменяла прежний разбор userId через map на структуру. Изменились порядок 401/400, сообщения ошибок userId и JSON-ответ при штатном отказе в разрешении. Строковое поле comment в структуре также начинало отклонять ранее игнорируемые значения неизвестного старому API поля.

Восстановлены:

- Проверка наличия session до разбора body.
- Точные проверки ключа `userId`, его строкового типа и прежние JSON-сообщения 400.
- Ответ `{ "message": ..., "code": ... }` на штатный отказ permission-сервиса в старых маршрутах. Технические ошибки auth продолжают закрывать доступ; scoped-ошибки APIREF могут давать предусмотренный этапом 2 ответ 503.
- Передача исходного body следующему handler, как в старом middleware.

Комментарий считывается опционально; у сотрудника/администратора его отсутствие не препятствует старому запросу. Для manager он проверяется отдельно и остаётся обязательным по требованиям этапа 2. В JSON по-прежнему нельзя назначить серверного автора/тип действия.

Файл: `internal/timeaccess/policy.go`.

### 3. Сдвиг даты при RFC3339 со смещением — исправлено для используемого UTC [С]

Прежний SQL-драйвер форматировал `time.Time` через `v.In(mc.cfg.Loc)`. В текущей конфигурации проверены только безопасные параметры: `loc=UTC`, `parseTime=true`; реквизиты подключения в отчёт не включены. Новая `entryDate` брала год/месяц/день исходного timezone и сразу создавала полночь UTC. Например, `2026-11-01T00:00:00+03:00` прежде попадало в DATE `2026-10-31`, а после этапа 1 стало попадать в `2026-11-01`.

Перед усечением теперь выполняется перевод в UTC. Предварительные блокировки батча и диапазона используют ту же дату, чтобы на границе месяца не блокировался другой месяц. Проверка месяца в новом timesheet edit API тоже производится по UTC — нельзя принять ноябрьский URL и фактически изменить октябрьскую запись.

Доказательство — сравнение прежней передачи time.Time в SQL, исходников установленного `go-sql-driver/mysql v1.10.0` (`packets.go`, `connection.go`) и нового нормализатора. Реальный SQL-прогон дат не выполнялся. Обычные даты с `Z` не меняются. Расширение поддержки иных DSN timezone в этот аудит не входит.

Файлы: `internal/adapter/mysql/sqlc/time_entry_audit.go`, `internal/timesheet/handler.go`.

Новые `expectedRevision` и поля timesheet API не стали обязательными для старых create/update/delete. Старые запросы сотрудника и администратора не требуют comment, actor, статуса подтверждения, department/company или новых флагов. Для новой scoped-ветки manager комментарий требуется намеренно. Старые endpoints не возвращают 409 из-за новой ревизии: изменение просто проходит общий аудит; optimistic check требуется при подтверждении/снятии.

## Отпуска, больничные, автоматические изменения [С]

Прослежены все вызовы Create/Update/DeleteUserTimeEntry(s), SQL-записи user_time_entries и Raw-вызовы. Raw-методы вызываются только внутри аудируемого writer. Новых обходов не обнаружено.

- **Отпуск:** создание сразу approved, утверждение, возврат approved в pending и удаление approved передают проверенного HTTP-автора и source vacation. Вызовы createOrUpdateVacationTimeEntries/deleteVacationTimeEntries идут с transactionQueries. Проверены сохранение часов при постановке vacation, прежний расчёт отпускных дней, удаление нулевых записей и восстановление work/office у записей с часами. Изменения времени и отпускного workflow находятся в общей транзакции. Pending-редактирование, отзыв и решение отдела сами по себе время не меняют. Права отпускного модуля не заменены timesheet-правами.
- **Больничные старого модуля:** запись больничного и medical-дней теперь атомарна; удаление и восстановление work тоже в общей транзакции. При восстановлении work сохранена нормализация office, которая раньше выполнялась user_time_entry.Service. Смена official/unofficial время не меняет. Маршруты и проверки owner/all сохранены. Не требуется включение неиспользуемой страницы больничных.
- **Текущий пользовательский medical-сценарий:** проходит обычный старый calendar API; нормализация и права сотрудника сохранены.
- **Напоминания:** существующий ticker только читает календарь и отправляет уведомления, не пишет user_time_entries; новый actor-контекст ему не требуется.
- **Глобальные calendar_events:** это отдельные записи календаря. Их права/SQL и наложение на пользовательские дни не изменены. Отдельного фонового writer времени в найденных исходниках нет. Для будущих доверенных внутренних writer нужен явный WithSystem; автоматического system fallback не возвращено.

Проверка исходников не доказывает отсутствие deadlock при реальной нагрузке или успешность внешней рассылки. Уведомления кадровых процессов вызываются после commit, их реальные каналы не запускались.

## Миграции 043/044 [С + официальная документация; выполнение — БД]

На этом аудите DDL и migrate.go не изменялись, новая миграция не добавлялась.

- 043: две таблицы создаются IF NOT EXISTS. Новый FK RESTRICT сначала добавляется, затем старый FK снимается. Точечный helper проверяет таблицу/колонки/правила существующего FK, пропускает уже выполненные шаги и запрещает снятие старого FK без проверенного нового. Проверены состояния: нет таблиц; создана одна/обе; оба FK; только новый; все DDL выполнены, но файл ещё не записан в schema_migrations.
- 044: два отдельных однострочных CREATE TRIGGER. Общий splitter не требует DELIMITER или разбора BEGIN/END. Уже существующий триггер пропускается только после проверки timing/event/table/body; неизвестное определение останавливает миграцию. DROP действующей защиты при повторе отсутствует. Проверены состояния после первого CREATE, после обоих CREATE и до регистрации файла.
- `.ddl` включён в embed/сборщик и следует за 043. sqlc его намеренно не разбирает; parse SQL генератора не доказывает синтаксическую исполнимость trigger DDL на сервере. Старые reference-файлы migrate_001.sql/schema.sql содержат только комментарии и не возвращают каскадный FK.
- MySQL выполняет DDL с implicit commit: SQL-транзакция migrator не даёт общего rollback файла; именно поэтому нужен повтор отдельных шагов. [Руководство MySQL](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html).
- Раздельный ADD/DROP не зависит от ограничения совмещённого ALTER для COPY. Проверка FK не отключается. [FOREIGN KEY MySQL](https://dev.mysql.com/doc/refman/8.0/en/create-table-foreign-keys.html).
- Конструкции таблиц рассчитаны на MySQL 8, как уже существующая схема с utf8mb4_0900_ai_ci. Для реального enforcement CHECK требуется MySQL 8.0.16+. Версия работающего сервера не определена без подключения; совместимость с фактическим экземпляром и MariaDB этим аудитом не подтверждена. [CHECK MySQL](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html).
- Для CREATE TRIGGER требуются права мигратора, а конфигурация binary logging может добавлять требования. Фактические grants/definer/server settings не проверялись. [CREATE TRIGGER MySQL](https://dev.mysql.com/doc/refman/8.0/en/create-trigger.html).

Повторное применение оценено по коду, не исполнено на MySQL. Уже зарегистрированный файл migrator пропускает целиком: он не восстанавливает вручную удалённые DBA таблицы/триггеры. IF NOT EXISTS также не доказывает соответствие произвольно изменённой существующей таблицы ожидаемой схеме. Механизм глобальной миграционной блокировки в этом узком аудите не переписывался.

## Обязательные ручные сценарии [БД — не выполнены]

На отдельной копии БД и с отдельными сессиями выполнить:

1. Обычный сотрудник без comment/revision создаёт work-дни старым create, меняет часы/location старым update, удаляет старым delete. Повторить для medical. Проверить прежние 201/204, календарь и статистику, фактический actor employee.
2. Администратор с отдельными all:create/edit/delete повторяет операции для другого сотрудника без manager-назначения и comment. Отдельно read-only/edit-only пользователь не должен подтверждать; edit не должен дать create/delete. Отключённый APIREF не должен мешать разрешённой административной операции.
3. Проверить ошибки старых маршрутов: нет cookie + некорректное body → 401; нет userId/нестроковый userId → прежние JSON 400; штатный отказ → JSON message/code 403. Auth с пустым ID → 401, без system.
4. Сравнить Z-дату и RFC3339 со смещением на границе месяца/года: например 2026-11-01T00:00:00+03:00 соответствует прежней UTC-дате 2026-10-31. Проверить owner/date истории и ревизию именно октября, отсутствие записи в ноябре. Для нового PUT с ноябрьским URL эта дата должна дать 400. Повторить create/update/delete.
5. В одном батче изменить два месяца; затем вызвать ошибку в последней сущности. Проверить полный rollback, включая историю и состояния месяцев. Повторить no-op и удаление отсутствующей даты.

## Оставшиеся риски и границы

- Не подтверждены фактическая версия MySQL, grants, SQL modes, применимость DDL, планы/время блокировок, восстановление после реального разрыва соединения и конкурентные сценарии. Это требует БД, а не дополнительных предположений из сборки.
- Нельзя одновременно оставлять старые пишущие экземпляры до этапа 1: они не используют общий аудит и месяцовые блокировки. Развёртывание/откат должны учитывать эту совместимость; историю нельзя удалять ради rollback.
- Deadlock/lock timeout возвращают ошибку с rollback; автоматический retry не добавлен. Два параллельных процесса migrator могут конкурировать за запись schema_migrations — глобальный механизм изначально не предусматривал блокировки.
- Нормы и глобальные календарные события не являются user_time_entries: их изменение не увеличивает revision месяца. Это граница согласованной модели содержимого времени; пересмотр её при изменениях нормативов не добавлялся.
- Для старых work-записей без истории нельзя восстановить системное происхождение. Кадровые нерабочие записи защищены по текущему типу; текущие записи с зафиксированным системным/кадровым происхождением дополнительно защищены по истории.
- Пользовательский CRUD дат проверен относительно текущего UTC DSN. У кадровых процессов до этапа 1 уже были сравнения date-map по time.Time/location; нет подтверждения полного корректного поведения произвольных offset-дат и иных DSN timezone. Нужен отдельный ручной прогон перед использованием таких форматов; посторонний рефакторинг кадровой обработки дат не выполнялся.
- Новый список табелей зависит от существующего authservice профилей; неизвестный пол даёт statisticsUnavailable. Его нельзя считать доказательством сохранения числовой статистики без сравнения на реальных данных.
