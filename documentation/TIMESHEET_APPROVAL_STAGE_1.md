# Подтверждение месячных табелей — этап 1

Реализована только серверная основа из промта №1: модель месяца, ревизии и аудит изменений времени. Frontend, маршруты подтверждения, новые права и политика доступа руководителей из промта №2 не добавлялись.

## Модель и ревизии

`timesheet_months` имеет первичный ключ `(user_id, year, month)` и поля:

- `status`: `pending`, `approved`, `needs_review`;
- `revision`: число реальных изменений записей месяца;
- `approved_revision`, `approved_by`, `approved_at`: последнее подтверждение;
- `updated_at`.

При отсутствии строки внутренний `timesheet.Service.GetMonth` возвращает `pending`, `revision=0`, без подтверждения. Существующие записи времени не пересоздаются, фиктивная история за прошлые изменения не генерируется. Исходная ревизия существующего содержимого — 0.

При реальном create/update/delete ревизия соответствующего календарного месяца увеличивается на 1 на каждую изменённую запись. `approved` становится `needs_review`; `pending` остаётся `pending`, `needs_review` сохраняется. Данные последнего подтверждения остаются для аудита, но статус явно показывает его неактуальность. Повторное подтверждение будет реализовано отдельным этапом.

Подтверждённое состояние дополнительно защищено CHECK: `approved_revision=revision`, автор и дата должны быть заполнены. Границы года/месяца и неотрицательность ревизии проверяются схемой и внутренним сервисом.

## Аудит и конкурентность

`time_entry_history` хранит владельца и дату независимо от `entry_id`, автора, `actor_type`, источник, тип операции, JSON до/после, комментарий, ревизию месяца и время события. Снимки содержат `entryId`, `dayTypeId`, `hoursWorked`, `workLocation`. Часы сохраняются точной десятичной строкой из MySQL; отсутствующая локация — JSON null. У создания отсутствует before-снимок, у удаления — after-снимок.

Операции над исходными записями, аудит и ревизии выполняются в одной транзакции. При использовании `Queries.WithTx` аудит входит в уже открытый workflow; при самостоятельном вызове repository-метода транзакция создаётся внутри обёртки. Ошибку записи аудита нельзя игнорировать: вызывающие операции возвращают её и откатывают транзакцию.

Сначала создаются/блокируются строки месяцев в порядке user/year/month, затем читаются текущие записи `FOR UPDATE`. Перед записью и после неё сравниваются фактические значения из БД. Это учитывает каноническое представление DECIMAL: `8` и `8.00` не считаются различными часами. Часы, тип дня и локация без реального изменения не создают события и не сбрасывают подтверждение. Удаление отсутствующей записи также ничего не меняет. При такой операции может появиться строка pending/revision=0 — она эквивалентна отсутствующему состоянию.

Батчи пользователя заранее блокируют все затрагиваемые месяцы, включая переход года; системные операции блокируют диапазон месяцев перед чтением текущих записей. Изменения одного месяца сериализованы. При ошибке внутри батча откатываются все его записи, история и ревизии. Возможный deadlock MySQL приводит к ошибке и откату, а не к частичному успеху; автоматического повтора не добавлено.

Идентификация автора:

- прямые изменения календаря собственного времени — `employee`, user_id сессии, источник `calendar`;
- действующие административные операции над чужим временем — `admin`;
- отпускные записи от административного workflow — `admin`, источник `vacation`, комментарий финального решения при наличии;
- больничный через календарь — обычные операции календаря с типом `medical`;
- старый модуль больничных — текущий пользователь employee/admin, источник `sick_leave`;
- доверенный внутренний вызов с явным `timeaudit.WithSystem(ctx, source)` — `system`, actor_id NULL; отсутствие автора само по себе больше не даёт system-доступ.

Тип `manager` предусмотрен схемой, но пока явно запрещён валидатором контекста. Допуск этого типа потребует проверенной политики прав/отдела из промта №2; сейчас ни один HTTP-обработчик его не назначает. Actor ID/type не принимаются из тела старых HTTP-запросов. Новые поля старым клиентам передавать не требуется.

Журнал append-only: в приложении нет операций его изменения/удаления, а два DB-триггера запрещают UPDATE и DELETE через SIGNAL SQLSTATE 45000. История не имеет каскадных связей с исходными записями и переживает удаление/пересоздание времени. Как и любую таблицу MySQL, её может изменить DBA через структурные операции; рабочей учётной записи не следует выдавать право обходить схему через DROP/TRUNCATE или удаление триггеров.

## Закрытые пути записи времени

| Путь | Покрытие |
| --- | --- |
| `POST /v1/usertimeentries/create` | Создание каждой записи, нормализация локации как раньше, один commit всего батча |
| `POST /v1/usertimeentries/update` | Тип, часы, локация, no-op, батч нескольких месяцев |
| `POST /v1/usertimeentries/delete` | Все реально удалённые даты, включая месяцы без оставшихся записей |
| Старые repository-методы Create/Update/Delete, включая singular и plural | Сигнатуры сохранены через handwritten-обёртки; новые внутренние Raw-методы вызываются только из общего аудита |
| Создание сразу утверждённого отпуска | Отпуск, время, история времени и ревизии в транзакции создания |
| `/vacation/:id/approve`, `/status` | Добавление/замена отпускных дней и восстановление при возврате из approved в pending |
| Удаление утверждённого отпуска | Сам отпуск и восстановление/удаление его времени теперь в одной транзакции |
| Предварительное согласование отдела, pending-редактирование или отзыв pending-отпуска | Время не меняется; аудита времени и увеличения ревизии нет |
| Старое создание/удаление больничного | Больничный и все его изменения времени теперь в одной транзакции, с тем же сохранением часов и восстановлением рабочего типа/локации |
| Изменение official/unofficial больничного | Как раньше, времени не меняет; аудит времени не создаётся |
| Удаление/переименование первичного ID используемого типа дня | FK теперь RESTRICT вместо CASCADE: скрытые изменения времени запрещены |

Страница больничных сейчас не используется. Основной ручной сценарий medical-дней выполняется через календарь; старый модуль сохранён и покрыт для отсутствия обхода аудита.

`calendar.Service` только читает время; его расчёт календаря, нормы часов и статистические формулы не изменены. SQL-запросы расчётов не переписаны. Имеющиеся HTTP-маршруты, permissions, тела запросов и ответы сохранены. В `cmd/api.go` изменена только передача DB в старый сервис больничных для его общей транзакции.

## Миграции и генерация

1. `043_timesheet_approval_audit.sql`: таблицы состояния/аудита и замена FK времени на RESTRICT. Новые таблицы создаются с IF NOT EXISTS. Новый FK `user_time_entries_day_type_audit_fk` добавляется отдельным шагом до удаления старого. Для этих двух конкретных ALTER migrator сверяет фактические ограничения через information_schema и безопасно продолжает после частичного выполнения.
2. `044_time_entry_history_immutability.ddl`: два триггера защиты истории. DROP отсутствует. Migrator проверяет имя, таблицу, событие, момент BEFORE и тело существующего триггера; совпадающий триггер сохраняется, отличающийся вызывает ошибку. При отсутствии выполняется CREATE. Частично применённый первый триггер не удаляется при повторе.

Расширение `.ddl` нужно потому, что фактический MySQL-парсер sqlc v1.31.1 не разбирает CREATE TRIGGER. Этот файл не участвует в разборе схемы sqlc, но включён в embed и общий упорядоченный migrator. Изменения `migrate.go` ограничены включением/сбором `.ddl` и узкими проверками конкретных FK/триггеров миграций 043/044. Разбиение SQL и исполнение остальных миграций не переписывались. Каждая команда триггера односоставная, без DELIMITER/BEGIN-блоков.

Для применения нужны права CREATE/ALTER и TRIGGER у пользователя migrator. Все миграции проекта выполняются при запуске backend. В рамках реализации миграции и живые проверки MySQL не запускались. SQLc проверил `.sql`-схему и запросы; триггерный DDL проверен чтением, но его исполнение в MySQL ещё требует ручной проверки.

Развёртывание: остановить старые экземпляры, применить миграции штатным запуском новой версии и затем разрешить запись. Не смешивать пишущие старые и новые версии: старые бинарники не содержат общего аудита. Прямые ручные изменения `user_time_entries` вне нового repository-слоя также не выполняют аудит приложения и не должны использоваться как рабочий путь редактирования.

Откат схемы автоматически не выполняется. Таблицы/историю сохранять; изменение FK обратно и удаление триггеров — отдельные согласуемые операции. Возврат старой пишущей версии означает потерю гарантий аудита и ревизий, поэтому при откате записи следует остановить. Фиктивный backfill истории/подтверждений не добавлен.

## Ручная проверка в тестовом окружении

Использовать отдельную тестовую БД и аккаунты. Все UUID, session и даты ниже заменить на данные тестового окружения. Не выполнять подготовительные SQL-изменения в production.

### Подготовка и наблюдение

После согласованного запуска миграций проверить:

```sql
SHOW CREATE TABLE timesheet_months;
SHOW CREATE TABLE time_entry_history;
SHOW CREATE TABLE user_time_entries;
SHOW TRIGGERS WHERE `Table` = 'time_entry_history';
SELECT id, system_name FROM day_types WHERE system_name IN ('work', 'medical', 'vacation');
```

Задать в SQL-сессии тестового владельца:

```sql
SET @owner = '<user_id>';
SELECT * FROM timesheet_months WHERE user_id = @owner ORDER BY year, month;
SELECT id, user_id, entry_date, entry_id, actor_id, actor_type, source,
       operation, before_values, after_values, comment, month_revision
FROM time_entry_history WHERE user_id = @owner ORDER BY id;
```

До первой записи строка месяца может отсутствовать: внутренний сервис считает её pending/revision=0. Никаких HTTP-endpoints состояния/подтверждения на этапе 1 нет.

### 1. Создание и граница месяца

С существующей сессией сотрудника выполнить запрос к штатному create (201):

```sh
curl -i -X POST 'http://localhost:8080/v1/usertimeentries/create' \
  --cookie 'session=<session>' -H 'Content-Type: application/json' \
  --data '{"userId":"<user_id>","entities":[{"dayTypeId":"<work_id>","hoursWorked":"8","entryDate":"2026-11-03T00:00:00Z","workLocation":"office"},{"dayTypeId":"<work_id>","hoursWorked":"7.5","entryDate":"2026-12-01T00:00:00Z","workLocation":"remote"}]}'
```

Выбрать предварительно свободные даты. Ожидать две записи времени, два create-события, pending/revision=1 отдельно для ноября и декабря. Для декабря/января проверить границу года. JSON after содержит фактические `8.00`/`7.50`, dayTypeId, location и entryId; actor — employee текущей сессии, source calendar.

### 2. Подтверждённый месяц и no-op

HTTP-подтверждение относится к следующему этапу. Только в тестовой БД имитировать уже подтверждённое состояние:

```sql
UPDATE timesheet_months
SET status = 'approved', approved_revision = revision,
    approved_by = '<admin_id>', approved_at = CURRENT_TIMESTAMP
WHERE user_id = @owner AND year = 2026 AND month = 11;
```

Обновить запись теми же значениями через штатный update (204):

```sh
curl -i -X POST 'http://localhost:8080/v1/usertimeentries/update' \
  --cookie 'session=<session>' -H 'Content-Type: application/json' \
  --data '{"userId":"<user_id>","entities":[{"dayTypeId":"<work_id>","hoursWorked":"8.00","entryDate":"2026-11-03T00:00:00Z","workLocation":"office"}]}'
```

Ожидать прежний approved, ту же revision и отсутствие новой истории. Затем изменить 8 на 6: ровно одно update-событие с before/after, revision+1, status needs_review. approved_by/at/revision сохраняются как последнее утратившее актуальность подтверждение. Ещё одна реальная правка сохраняет needs_review и увеличивает revision; no-op не увеличивает её.

### 3. Локация и тип дня

Изменить только office → remote при прежних часах: update-аудит, revision+1. Изменить тип на medical: сохранить прежние бизнес-правила часов, workLocation становится NULL, before/after отражают изменение. Повторить medical с теми же часами — no-op. Создать medical-день с нулевыми часами и удалить его через календарь — create/delete и соответствующие ревизии. Это основной действующий сценарий больничных.

### 4. Удаление и пересоздание

```sh
curl -i -X POST 'http://localhost:8080/v1/usertimeentries/delete' \
  --cookie 'session=<session>' -H 'Content-Type: application/json' \
  --data '{"userId":"<user_id>","entryDate":["2026-11-03T00:00:00Z","2026-12-01T00:00:00Z"]}'
```

Ожидать 204, delete-события с before и NULL after, увеличение каждого затронутого месяца. Повторное удаление не создаёт историю и не увеличивает revision. Пересоздание той же даты имеет новый entry_id и create-событие; старая история остаётся доступна по owner/date.

### 5. Откат батча

В create передать свободную корректную дату, а затем дату с несуществующим dayTypeId. Ожидать существующую обработку ошибки и отсутствие любой частичной записи, новой истории или изменения ревизии. Аналогично проверить update-батч: успешная первая правка + недопустимый FK второй должны целиком откатиться.

### 6. Конкурентность

В двух терминалах одновременно обновить одну дату разными часами. История должна образовать последовательную цепочку before → after, ревизии без потерь, ранее approved становится needs_review. Одновременный одинаковый update даёт только одно реальное изменение. Параллельные create одной даты не нарушают unique(user_id, entry_date); неуспешная операция не оставляет аудит/ревизию. Повторить батчи ноября/декабря с обратным порядком входных дат.

### 7. Административный автор

Через прежние разрешения календаря изменить чужое время администратором. В истории actor_id администратора, actor_type admin, owner остаётся сотрудником. Собственное время фиксируется как employee-действие. Новые права руководителей не выдавались этим этапом.

### 8. Отпуска

- Утвердить pending-отпуск, включая период на границе месяца: реальное создание/обновление vacation-дней аудируется с source vacation и автором администратора.
- Проверить создание сразу approved через существующий административный API.
- Вернуть approved-отпуск на pending и удалить утверждённый отпуск: нулевые vacation-записи удаляются; дни с часами восстанавливаются в work/office как раньше; каждому реальному изменению соответствуют история и ревизия.
- Предварительное согласование отдела и pending-отзыв/редактирование не меняют время и его ревизии.
- При ошибке системной записи весь отпускной workflow откатывается вместе с временем/аудитом.

### 9. Дополнительный старый модуль больничных

Не требует возвращения его страницы в интерфейс. При необходимости через существующие endpoints создать/удалить старый sick_leave, включая несколько месяцев. Проверить сохранение часов, medical-тип, восстановление work/office и atomic rollback. official/unofficial не меняют время и не создают аудит времени. Обычные пользователи сейчас проверяют medical-дни по пункту 3.

### 10. Системные вызовы

Для доверенного внутреннего вызова с явным timeaudit.WithSystem проверить actor_id NULL, actor_type system и указанный источник. Без actor-контекста операция должна завершиться ошибкой и не изменять время. Для проверки можно использовать существующий внутренний сценарий в тестовом окружении; отдельного публичного незащищённого endpoint не добавлено.

### 11. Неизменяемость истории и каскады

В тестовой SQL-сессии попытки UPDATE/DELETE конкретного события должны завершиться SQLSTATE 45000:

```sql
START TRANSACTION;
UPDATE time_entry_history SET comment = 'attempt' WHERE id = <history_id>;
ROLLBACK;
START TRANSACTION;
DELETE FROM time_entry_history WHERE id = <history_id>;
ROLLBACK;
```

Попытка удалить используемый day_type через API по-прежнему запрещена; прямой DELETE/изменение его первичного ID запрещается FK RESTRICT и не уничтожает время незаметно. Не выполнять DROP/TRUNCATE — это обход схемы с административными правами, а не рабочий сценарий.

## Граница этапа

Не реализованы намеренно: HTTP-согласование, ожидаемая клиентская ревизия/409, права руководителя на табели, исправления руководителем с обязательным комментарием, новые UI/отчёт/история в интерфейсе. Это промты 2–4; переход к ним требует отдельного указания пользователя.

## Исправления после code review — 18.11.2026

- Удалён неявный перевод пустого actor_id в system. HTTP-контекст конструируется только с непустым строковым user_id из проверенной сессии; иначе до вызова сервисов возвращается 401. Дополнительно permission middleware проверяет непустой user ID, а auth-клиент различает отсутствие идентичности и другие отказы сервиса.
- Общий writer проверяет контекст до открытия собственной транзакции и любых изменений. Raw-запросы остались только внутри этого же writer, новых обходов не добавлено.
- Для внутренних операций введён явный WithSystem. Простой WithActor(Type=system) без внутренней метки запрещён. HTTP-контекст сохраняет метку происхождения, поэтому WithSystem/WithSource поверх него не позволяют записать system-аудит.
- Старый внутренний сценарий удаления больничного сохраняет явный system-контекст, а не переименовывает его в пользовательский admin.
- Manager остаётся зарезервированным и отклоняется до реализации и проверки политики прав на следующем этапе.

Для 043 устранена зависимость от совмещённого DROP/ADD FOREIGN KEY: MySQL поддерживает такое сочетание только с INPLACE, а не COPY. Вместо отключения проверки FK используются два отдельных шага с проверкой фактической схемы. Это ограничение описано в [официальном руководстве MySQL 8.0](https://dev.mysql.com/doc/refman/8.0/en/create-table-foreign-keys.html). Для 044 исключено снятие уже действующей защиты истории при повторе. Развёртывание по-прежнему требует остановки старых пишущих экземпляров.
