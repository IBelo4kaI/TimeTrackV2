# Руководители отделов и уведомления

## Настройки и доступ

В существующих настройках добавлена вкладка «Руководители отделов».
Администратор выбирает отдел и сотрудника из живого справочника, компания определяется автоматически по сотруднику; backend повторно проверяет соответствие данных при сохранении. Frontend mock-списки не используются. Несколько руководителей одного отдела допустимы; дубли одного назначения запрещены. Назначение удаляется отдельно, без удаления сотрудника.

Просмотр: `time:system_settings:read`. Создание, удаление и повтор назначения роли: `time:system_settings:edit`.

Справочник становится источником назначений. Для согласования и scoped-чтения файлов одновременно требуются:

1. Сессия и существующее право `time:department.manager:manage`.
2. Назначение пользователя руководителем в локальном справочнике.
3. Совпадение подтверждённых компании и отдела руководителя и сотрудника через живой APIREF.

Удаление назначения закрывает scoped-доступ даже при сохранённом permission. Перевод сотрудника/руководителя в другой отдел делает старое назначение неприменимым: нужно удалить его и создать актуальное. Самосогласование по-прежнему запрещено. Финальное утверждение/отклонение администратором не зависит от справочника руководителей или APIREF.

После развёртывания требуется заполнить справочник: одного ранее выданного permission теперь недостаточно. Доступ администратора с прежними глобальными правами сохраняется.

## Настройка и синхронизация роли

На вкладке «Руководители отделов» добавлены поле ID роли и действия «Сохранить» / «Удалить ID роли». Значение хранится в существующем `system_settings` под ключом `department_manager_role_id`, а не в env. Для изменения требуется `time:system_settings:edit`, для чтения — `time:system_settings:read`. Пустое значение отключает выдачу роли новым назначениям. ID является непрозрачной строкой длиной до 255 символов без управляющих символов.

Auth-клиент использует существующие `AUTH_SERVICE_HOST` и `AUTH_SERVICE_API_KEY`; ключ передаётся в cookie `session`. Запросы:

- `POST /api/as/users/roles/add`;
- `POST /api/as/users/roles/remove`;
- JSON обоих запросов: `{ "role_id": "...", "user_id": "..." }`.

Перед изменением проверяется наличие роли в существующем `GET /api/as/users/timetrack`, чтобы повтор не добавлял уже существующую роль и не снимал отсутствующую. Остальные роли сотрудника не заменяются. HTTP non-2xx, HTML вместо API-ответа, таймаут и недоступность сервиса не считаются успехом. Redirects не выполняются; токен и тела запросов изменения ролей не логируются.

`RoleAssigner` подключён к auth-клиенту через `EnsureRole` и `RemoveRole`. После создания назначения backend пытается добавить настроенную роль. В назначении сохраняется фактически применённый `auth_role_id` и статус:

- `pending`: первоначальное состояние до синхронизации;
- `not_configured`: ID роли пуст;
- `synced`: роль приведена к настройке;
- `failed`: назначение/снятие роли завершилось ошибкой; доступен повтор.

При изменении настройки существующие роли массово не меняются. Интерфейс показывает необходимость синхронизации; «Синхронизировать роль» снимает прежнюю роль, если она не используется другими назначениями этого сотрудника, и назначает новую. Если настройка очищена, синхронизация снимает сохранённую роль. Пустая настройка не теряет информацию о ранее выданной роли: она сохранена в назначении и будет использована при удалении/синхронизации.

При удалении назначения backend снимает сохранённую роль только когда она больше не используется другими назначениями того же пользователя. При отказе auth-сервиса назначение сохраняется со статусом ошибки, DELETE возвращает 503; можно повторить удаление. Для старых назначений без сохранённого `auth_role_id` роль не угадывается и не снимается — сначала нужна синхронизация.

Изменения ролей и удаление назначений сериализуются блокировкой строки настройки и записи назначения. Системная настройка не блокирует работу финального отпускного workflow. Распределённой транзакции между MySQL и auth-сервисом нет: если удалённое изменение прошло, а запись результата в MySQL сорвалась, необходимо повторить синхронизацию; такая ошибка не выдаётся за подтверждённый успех. Фоновая очередь автоматических повторов не добавлена.

Используйте отдельную роль руководителя отдела: при удалении последнего назначения сохранённая роль снимается и в случае, если она уже существовала до первой синхронизации. Роль должна содержать `time:department.manager:manage`; назначение произвольной роли само по себе не обходит существующие серверные проверки permission и отдела.

Новые env-переменные и feature flags не добавлялись. APIREF продолжает использовать пользовательскую сессию; служебный API-ключ используется только при обращениях к auth-сервису.

## Уведомления

При создании pending-заявки руководители её компании/отдела берутся из нового справочника. Каждого получателя backend повторно сопоставляет с живым APIREF; отсутствующие, неоднозначные и переведённые в другой отдел сотрудники исключаются. Автор собственной заявки исключается.

Каналы: существующие уведомления приложения/SSE и VK. Текст содержит имя сотрудника, период и тип отпуска, ссылка открывает страницу заявки. Личное описание заявки в новую рассылку руководителям не добавляется. Для VK сохраняются существующие настройки/привязки пользователей.

Существующая рассылка администраторам сохраняется. При создании заявки пользователь, уже включённый в список администраторов-получателей, не получает вторую копию как руководитель.

Повторная рассылка руководителям вызывается после:

- изменения дат или типа pending-заявки;
- редактирования ранее согласованной/отклонённой отделом заявки, сбрасывающего решение;
- возврата заявки администратором на рассмотрение.

Обычное повторное сохранение pending-заявки без изменения дат/типа не создаёт повторной рассылки. Решение руководителя и окончательное утверждение не создают уведомление о необходимости согласования.

Отправка выполняется после commit заявки, по существующему best-effort механизму. Сбой APIREF, отсутствие получателей или ошибка доставки не отменяют сохранение заявки. Отложенной очереди и гарантированного повторения доставки нет. Если APIREF не разрешает сессии автора видеть данные руководителя, получатель не определяется и уведомление не отправляется; расширение прав по умолчанию не используется. Сессии не сохраняются для фоновых повторов.

## Миграция и API

Миграция `041_department_managers.sql` добавляет таблицу `department_managers`: UUID, company, department, user_id, created_by, role_sync_status, timestamps; уникальный ключ company + department + user_id. Сравнение названий компании/отдела сохраняет регистр, пробелы по краям удаляются перед сохранением.

Новая миграция `042_department_manager_role.sql` добавляет `department_managers.auth_role_id` и создаёт пустую настройку `department_manager_role_id`, сохраняя существующее значение при повторе. Migrator допускает повтор только этого конкретного ADD COLUMN при частично выполненной DDL-миграции.

Миграция не запускалась. Как и другие миграции проекта, она будет применена штатным migrator при запуске новой версии backend. Для безопасного отката можно вернуть прежние приложения и оставить добавленную таблицу. Автоматический down и удаление данных не выполнялись. Для отката новой версии можно оставить добавленные колонку и настройку: прежний код их игнорирует.

API:

- `GET /v1/department-managers`: сохранённые назначения и статусы назначения роли.
- `GET /v1/department-managers/employees`: подтверждённые пользователи APIREF с `userId`, `company`, `department`, без frontend fallback.
- `POST /v1/department-managers`: `{ "company": "...", "department": "...", "userId": "..." }`; успех 201. Поля берутся из подтверждённого списка, backend проверяет их повторно.
- `DELETE /v1/department-managers/:id`: удаление назначения, успех 204.
- `POST /v1/department-managers/:id/sync-role`: синхронизация с текущим настроенным ID роли; возвращает назначение с сохранённым `authRoleId` и фактическим статусом попытки. При пустой настройке прежняя отслеживаемая роль снимается, статус становится `not_configured`.

Настройка читается через существующий `GET /v1/system-settings/department_manager_role_id`, сохраняется/очищается через `POST /v1/system-settings/value` с `{ "settingKey": "department_manager_role_id", "settingValue": "..." }`. При очистке `settingValue` пустое.

Ошибки: 400 некорректный ввод, 401/403 по существующему session/permission middleware, 404 отсутствующее назначение, 409 дубль или несоответствие живому справочнику, 503 недоступный APIREF при получении кандидатов/создании назначения.

## Проверки и ручные сценарии

Выполнены `sqlc generate`, `gofmt`, сборки backend/frontend, `go vet ./...` с временным Go-кэшем, `git diff --check`. Новые автоматизированные тесты не писались. Миграции, живые API-запросы, отправка уведомлений и реальные изменения ролей не запускались. Frontend build имеет предупреждение Vite о крупных чанках.

Ручная проверка в тестовом окружении:

1. С правом settings:read назначения видны, без settings:edit изменение запрещено и в UI, и прямым запросом.
2. Выбрать отдел/сотрудника и сохранить; backend принимает только фактический scope из APIREF. Дубль даёт 409, разные руководители одного отдела допустимы.
3. При сбое APIREF старые назначения доступны для просмотра/удаления, новые создать нельзя; mock-данные не подставляются.
4. Пустая настройка даёт `not_configured`, запрос назначения роли не выполняется. Сохранить корректный ID и создать руководителя: выполняется POST roles/add, сохраняются authRoleId и synced. Неверный ID/403/ошибка сети дают failed и возможность повтора.
5. С назначением, permission и совпадающим живым scope руководитель видит/согласует заявки и читает файлы при `time:files:read`; без назначения или permission scoped-доступ запрещён. Чужая компания, чужой отдел и самоодобрение запрещены.
6. Удалить назначение и повторить прямые запросы: локальный scoped-доступ закрыт. Проверить, что глобальные права администратора работают как раньше.
7. Создать pending-заявку: уведомления приложения и VK получают руководители того же отдела/компании, автор исключён; руководитель из списка администраторов не получает дубль.
8. Изменить даты/тип, сбросить предыдущее согласование редактированием, вернуть финальную заявку на рассмотрение: приходит повторное уведомление руководителям. Повторное сохранение неизменной pending-заявки не создаёт новую рассылку.
9. При недоступном справочнике заявка сохраняется, рассылка по непроверенным получателям не производится, окончательное решение администратора доступно.
10. Повторить синхронизацию уже выданной роли: нет дублирующего добавления, прочие роли сохранены. Сменить ID роли и синхронизировать: старая роль снимается при отсутствии других назначений с ней, новая добавляется.
11. Очистить ID роли: новые назначения не получают роль. Для существующего назначения нажать синхронизацию: прежняя отслеживаемая роль снимается. Удаление назначения после очистки также использует сохранённый ID.
12. При ошибке roles/remove удаление назначения не завершается, запись остаётся со статусом failed, DELETE возвращает 503. Повтор после восстановления auth-сервиса удаляет роль и запись.
13. При нескольких назначениях одного пользователя с одной ролью удаление одного не снимает общую роль. Удаление последнего снимает её. Проверить параллельную синхронизацию/удаление — операции сериализуются.
14. Проверить сохранение/очистку настройки с settings:edit и запрет прямой записи без этого права; длинный ID/управляющие символы дают 400.
