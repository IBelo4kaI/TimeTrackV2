# HTTP 500 при чтении истории табеля

## Вывод и границы подтверждения

В актуальном коде найден и воспроизведён дефект: nullable JSON-колонки time_entry_history.before_values / after_values были сгенерированы sqlc как json.RawMessage без указателя. database/sql не умеет сканировать SQL NULL в этот тип. Создание записи штатно пишет NULL в before_values, удаление — в after_values. При чтении таких строк rows.Scan возвращает ошибку, которую обработчик преобразовывал в общий HTTP 500 без логирования.

Локальная диагностическая программа с минимальным database/sql-драйвером, возвращающим SQL NULL и JSON как []byte, до изменения получила:

```
sql: Scan error on column index 0, name "before_values": unsupported Scan, storing driver.Value type <nil> into type *jsontext.Value
```

В установленном Go 1.27.3 json.RawMessage отображается в сообщении как jsontext.Value; в других версиях имя типа может быть json.RawMessage. Диагностический индекс 0 относится к программе с двумя колонками; в настоящем ListTimeEntryHistory индексы before_values/after_values равны 8/9.

После перехода на *json.RawMessage та же диагностика завершилась без ошибки и сериализовала beforeValues:null, afterValues:{...}. Дополнительно DefaultParameterConverter подтвердил: nil-указатель передаётся в SQL как NULL, непустой снимок — как []byte. Это воспроизведение механизма сбоя, не HTTP/MySQL-интеграционная проверка. Программа находится вне репозитория; новые автоматизированные тесты не добавлены.

**Конкретный запрос работающего сервера локально не воспроизводился.** Нет подтверждения применённых на нём миграций, схемы, DSN, версии бинарника и содержимого строк. Поэтому нельзя объявлять серверный инцидент окончательно закрытым только по этой диагностике и сборке. Для подтверждения нужно повторить проблемный запрос после штатного развёртывания и получить безопасный серверный лог, описанный ниже.

## Путь запроса и место потери ошибки

1. cmd/api.go подключает timesheet.SetupRoutes с общим timeaccess.Policy и существующим slog.Logger приложения.
2. internal/timesheet/route.go регистрирует GET /:userId/:year/:month/history. Более короткие маршруты не совпадают с дополнительным сегментом history.
3. Handler.History проверяет год/месяц, затем Policy.Authorize(target, "read"). Только после разрешения выполняется чтение.
4. Service.History строит начало месяца UTC и исключительную границу следующего месяца, вызывает ListTimeEntryHistory.
5. В этом модуле отдельного слоя repository между Service и sqlc нет: Service хранит *repo.Queries. SQL из query/timesheet.sql генерируется в timesheet.sql.go.
6. ListTimeEntryHistory выполняет параметризованный SELECT user_id + диапазон entry_date и ORDER BY id. В generated rows.Scan колонки before_values/after_values читались по индексам 8/9 в json.RawMessage. Здесь возникает воспроизведённая ошибка.
7. Service возвращает ошибку, Handler передавал её в apiError, где fallback response.ServerError формирует ровно обобщённый JSON из сообщения об инциденте. Исходная ошибка не попадала в лог.

Ошибки QueryContext, Scan, Close и rows.Err передаются наверх; ни одна не заменяется успешной пустой историей.

## Исправление

В sqlc.yaml добавлены два column override для before_values и after_values: *json.RawMessage. Generated code сканирует **json.RawMessage: database/sql сохраняет nil для SQL NULL, выделяет значение для непустого JSON. Override сохраняется при последующих sqlc generate.

snapshotJSON возвращает указатель на непустой снимок и nil при отсутствии записи. Это адаптация типов к sqlc; SQL INSERT, состав снимка, операции, история и ревизии не изменены. JSON API сохраняет прежние значения: null либо объект, без дополнительной обёртки.

Service.History теперь явно возвращает ошибку до нормализации nil-среза. Успешное отсутствие строк превращается в непустой по типу, но пустой по содержимому срез, который сериализуется как []. Настоящий сбой БД остаётся HTTP 500.

Handler.History логирует ошибки отдельно для authorize, read_history и encode_response. Для этого используется существующий logger приложения. Клиентский ответ остаётся обобщённым; ожидаемые 400/401/403 и 503 сохраняют свои коды. Проверки доступа не менялись.

## Миграции, nullable, идентификаторы и даты — проверка по исходникам

- 043 создаёт before_values/after_values как JSON NULL, entry_id/actor_id как VARCHAR(36) NULL. Чтение соответствует колонкам и порядку SELECT; схема не изменялась.
- entry_id/actor_id остаются sql.NullString, которые корректно принимают NULL. Их существующая JSON-форма не менялась. UUID хранится как VARCHAR, не BINARY: при чтении нет преобразования байтов в UUID и ошибки такого преобразования.
- before/after являются типизированным JSON, не строкой с повторным JSON-кодированием. Локальная диагностика подтвердила сериализацию null/объекта. MySQL JSON гарантирует корректный JSON при штатной записи; фактическую схему работающего сервера всё равно нужно сверить.
- entry_date и created_at NOT NULL читаются в time.Time. Для MySQL необходим прежний parseTime=true в DB_STRING. DB_STRING не выводился и не менялся; его рабочее значение не проверялось соединением. Без parseTime ошибка Scan даты также возможна и теперь будет видна по колонке в безопасном логе. Нулевые/нестандартные даты и крайний диапазон DATE требуют проверки на фактической БД.
- Фильтр истории использует user_id и entry_date, а не JOIN с существующей user_time_entries. Поэтому удаление исходной записи не должно скрывать историю; пересоздание того же дня сохраняет предыдущие события с прежним entry_id и добавляет новые.
- AppendTimeEntryHistory выполняется в едином аудируемом механизме. Для create снимок before отсутствует, для update есть оба, для delete отсутствует after. Пересоздание снова имеет before=NULL. Сопоставление по user_id/date и ORDER BY id сохраняет последовательность.
- 044 запрещает UPDATE/DELETE истории триггерами. SELECT триггеры не вызывает; причина воспроизведённой ошибки — чтение nullable JSON, а не запрет изменения истории.
- Наличие файлов миграций в исходниках не доказывает применение на сервере. Реальная БД и её schema_migrations не проверялись.

## Авторизация — проверка по исходникам

History использует тот же Policy.Authorize, что и до изменения. Собственное время и разрешённый административный доступ проходят прежнюю проверку calendar/read; чтение чужих записей через manager-ветку требует department.manager:manage и актуальные назначения DepartmentScopeResolver.Members. Само разрешение без назначения доступ не выдаёт.

Отсутствующая/некорректная сессия возвращает 401, отсутствие права/назначения/сотрудника в scope — 403. Ошибка справочника или lookup назначений в manager-ветке преобразуется Policy в fiber.ErrServiceUnavailable (503), не в 500. Нет доступа по умолчанию. Если доступ уже разрешён основной административной веткой, resolver не вызывается. Ошибки авторизации в apiError распознаются через errors.As(*fiber.Error) до fallback 500.

Диагностика authorize логирует код зависимости 503, не исходные данные APIREF. Policy уже преобразует ошибку resolver в HTTP-код; эта задача не меняет его поведение и не добавляет сетевых запросов ради диагностики. read_history сохраняет доступные MySQL-коды непосредственно от repository.

## Безопасное серверное логирование

Место: internal/timesheet/history_errors.go, метод Handler.historyError; вызывается из Handler.History до формирования обобщённого ответа. Сообщение: `timesheet history failed`.

Поля:

- stage: authorize / read_history / encode_response.
- error_type: Go-тип ошибки.
- cause: mysql / sql_scan / sql_scan_null / deadline_exceeded / context_canceled / invalid_connection / http_dependency / internal.
- Для MySQL: mysql_number и sqlstate, без текста MySQL Message.
- Для Scan: column_index и column из фиксированного списка колонок запроса, без значений.
- Для HTTP-зависимости: http_status.

В лог не включены userId/actorId, даты запроса, URL, cookie, DSN, JSON-снимки, комментарии и SQL-параметры. Полный err.Error() не логируется: ошибка преобразования или MySQL может содержать данные. Для неизвестных ошибок остаются этап и тип; не следует добавлять дамп строки или полного SQL для выяснения причины.

Для подтверждения инцидента нужны одна строка `timesheet history failed` от повторного запроса и время выполнения. Не нужно присылать строку access-лога с идентификатором сотрудника. Для старой версии исходная ошибка была потеряна; один общий клиентский JSON не позволяет восстановить её задним числом.

До исправления NULL before/after соответствует Scan index 8/9. После исправления повторение `sql_scan_null` в этих колонках требует сверки, что на сервере действительно развёрнут regenerated code новой версии.

## Если схема не применена

MySQL 1146 у read_history означает отсутствие таблицы; 1054 — отсутствующую колонку; 1142 — недостаточные права SQL-пользователя. Код сам по себе не доказывает, почему схема отличается: нужно проверить метаданные на сервере по согласованной процедуре.

Ответственному за БД выполнить только чтение:

```sql
SELECT name FROM schema_migrations
WHERE name IN ('migrations/043_timesheet_approval_audit.sql',
               'migrations/044_time_entry_history_immutability.ddl');
SHOW CREATE TABLE time_entry_history;
SELECT COLUMN_NAME, DATA_TYPE, IS_NULLABLE
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'time_entry_history'
ORDER BY ORDINAL_POSITION;
SHOW TRIGGERS WHERE `Table` = 'time_entry_history';
```

Не выгружать строки истории и не менять их ради диагностики. Сверить структуру с 043 и определения двух append-only триггеров с 044; учитывать используемую MySQL и совместимость utf8mb4_0900_ai_ci.

Если миграции отсутствуют или выполнены частично — резервная копия, согласованное окно развёртывания и штатный мигратор с проверкой его результатов. Не запускать отдельное CREATE TABLE или правку истории из handler. Текущий cmd/main.go уже запускает все pending-миграции при старте приложения: обычный рестарт нельзя использовать как безопасную диагностическую команду без оценки всех ожидающих миграций. В этой задаче production-подключение, рестарт и миграции не выполнялись; механизм их запуска не менялся.

## Ручная проверка в тестовом окружении

1. Месяц без истории: авторизованный владелец получает 200 и ровно [], без новой истории или изменения ревизии от чтения.
2. Создать work штатным маршрутом: history возвращает create, beforeValues=null, afterValues=объект.
3. Изменить запись: появляется update с обоими объектами, старый create остаётся.
4. Удалить запись: delete с afterValues=null и заполненным beforeValues; весь день остаётся в истории.
5. Создать день снова: новый create с другим entryId и beforeValues=null. Предыдущие три события сохранены и упорядочены по id.
6. Проверить system-событие с actor_id=NULL, допустимый entry_id=NULL и workLocation=null: без Scan/JSON-ошибок, прежний контракт UUID-полей сохранён.
7. Собственный календарь сотрудника, история подчинённого руководителем и административная история: прежний доступ. Чужой отдел/manager без назначения — 403; нет сессии — 401; недоступность APIREF в manager-ветке — 503. Административная ветка не требует APIREF, если основное разрешение уже выдано.
8. В изолированном окружении воспроизвести отсутствие таблицы, несовпадение колонок или недостаточные SQL-права: настоящий 500, безопасный mysql_number в логе, не 200 []. Не менять production-схему ради проверки.
9. При любой повторной 500 получить строку timesheet history failed и сверить stage/cause/column/mysql_number с описанием выше; проверить версию развёрнутого бинарника. Не считать один успешный build подтверждением исправления рабочего сервера.
