# Руководители нескольких отделов и компаний

Реализовано назначение любого подтверждённого сотрудника APIREF руководителем любого подтверждённого целевого отдела. Собственные компания и отдел руководителя больше не определяют его полномочия. Новых миграций, систем ролей и переменных окружения нет.

## Backend

`DepartmentScopeResolver.Members` получает все строки department_managers по user_id через новый sqlc-запрос ListDepartmentManagersByUser. Из назначений строится множество точных пар company/department — ключ Go-структуры, без склейки строк и возможных коллизий разделителя. По свежему APIREF выбираются сотрудники этих пар, сам руководитель исключается.

Разрешения по-прежнему проверяются вызывающими модулями. department.manager:manage без сохранённых назначений не открывает доступ. В текущей схеме активное назначение — существующая строка таблицы; role_sync_status не является новым переключателем доступа. Ошибки чтения назначений/APIREF, отсутствующие или неоднозначные идентичности не заменяются разрешением по умолчанию. Сохраняется проверка присутствия самого руководителя в достоверном справочнике; его собственная пара не сравнивается с целевыми и не добавляет доступ автоматически.

Directory по-прежнему возвращает только валидные однозначные пары сотрудников: HTTP-status/JSON/размер/вложенность/пустые значения/дубликаты user_id проверяются прежним парсером. Employees использует тот же единственный парсер и возвращает дополнительно full_name для формы назначения. Directory является проекцией того же результата на пары; ФИО не участвует в сравнении scopes и не меняет авторизацию. Некорректное необязательное full_name не определяет достоверность компании/отдела; в интерфейсе есть fallback на прежний профиль или ID.

В Create теперь две независимые проверки:

1. Назначаемый userId присутствует в валидном APIREF.
2. Целевая company/department присутствует среди валидных пар справочника.

Совпадение собственного отдела кандидата с целевым не требуется. Прежние UUID/длина/trim-проверки и уникальность company+department+user_id сохранены. Неизвестная компания, отдел другой компании или невалидный кандидат дают ошибку до INSERT. Пустой отдел без однозначно подтверждённой пары в текущем контракте APIREF назначить нельзя.

GET `/v1/department-managers/employees` совместимо дополнен строкой fullName из full_name APIREF. Прежние userId/company/department сохранены; последние два поля кандидата описывают его фактическое место работы. Тело POST назначения осталось `{company, department, userId}`; company/department теперь явно выбираются как целевые.

## Единый доступ и совместимость

Поиск backend-вызовов выявил ограничения равенства собственного отдела только в старом Members, Create и выборе получателей уведомлений. Они заменены. Остальные потребители уже используют общий resolver:

| Модуль | Сохранённая проверка |
|---|---|
| Отпуска | DepartmentMembers → Members; чтение/список/решение по реальному владельцу заявки. DepartmentDecision отдельно запрещает самосогласование. |
| Табели | timeaccess.Policy.Members → Members для списка, статуса, истории, подтверждения и снятия. timesheet.all:approve остаётся независимым административным правом. |
| Календарь и время | Старые calendar/statistics/create/update/delete и новый PUT entries проходят общую policy. Комментарий и защита кадровых/system-записей manager не изменены. |
| Файлы отпусков | FileHandler.departmentReadAccess → Members, с прежними дополнительными files-проверками и ограничением entityType=vacation/read. Кеш результата только внутри одного запроса, не между запросами. |
| Администраторы | Прежние all-разрешения проверяются независимо; отсутствие назначения или недоступность APIREF не заменяет и не отменяет административную ветку. |

Сам руководитель исключён из Members, даже если назначен на собственный отдел. Самосогласование собственного отпуска/табеля в scoped-ветке остаётся запрещено; персональное чтение и отдельные административные разрешения не менялись.

Назначения не кешируются между запросами. После успешного удаления и commit следующая серверная проверка читает оставшиеся назначения. Удаление одной пары убирает только эту пару; остальные сохраняются. Уже выполняющийся запрос, который проверил scope до удаления, не отменяется задним числом.

Старые назначения собственного отдела остаются валидными без переноса данных. Изменение собственного места работы руководителя не отменяет его сохранённые целевые назначения, если личность по-прежнему подтверждена APIREF.

Виджет смежных отпусков на frontend описывает отдел выбранного заявителя, а не полномочия руководителя; он не заменяет backend scope и не переделывался.

## Роли

SyncRole, removeRoleIfUnused и Delete не изменялись: их участок исходника полностью совпадает с HEAD. Настройка department_manager_role_id и существующие auth endpoints add/remove сохранены.

При удалении проверяется CountOtherDepartmentManagersWithRole по user_id и тому же auth_role_id, исключая удаляемый id. При наличии другого назначения этой роли внешний RemoveRole не вызывается. После удаления последнего использующего роль назначения она снимается прежним способом. Назначения другой роли учитываются отдельно. Настройка роли и удаление по-прежнему сериализованы существующей транзакционной блокировкой настройки.

Если снять последнюю роль во внешнем auth не удалось, прежний Delete возвращает 503 и сохраняет назначение с ошибкой синхронизации. Это не успешное удаление, поэтому обещание прекращения доступа применяется после успешного commit удаления. Механизм ошибок и повторной синхронизации не менялся.

## Уведомления

notifyDepartmentManagers определяет актуальную пару заявителя через тот же Directory и получает назначения этой пары. Получатель должен присутствовать в достоверном APIREF, но больше не обязан работать в отделе/компании заявителя.

Сохраняются:

- Все назначенные руководители целевой пары как возможные получатели.
- Исключение автора заявки.
- Исключение повторных ID и получателей из excluded, в том числе уже уведомлённых администраторов.
- Прежние условия pending-заявки и pending-этапа отдела.
- Существующие отправка in-app/VK, текст и ссылка.

Ошибочный/недоступный APIREF или не подтверждённая личность получателя не включают fallback-рассылку. Механизм отдельной рассылки администраторам не изменён.

## Frontend

В существующем modal назначения последовательно выбираются целевая компания, её отдел, затем сотрудник из полного валидного списка кандидатов APIREF. Список сотрудников не фильтруется по выбранной паре. Переиспользован Autocomplete: поиск по ФИО, ID остаётся значением выбора, создание произвольной записи отключено.

Варианты и выбранный кандидат показывают фактические company/department, независимо от целевых. ФИО берётся из APIREF; если его нет, сохраняется прежний fallback usersAll/текущий пользователь/ID. Кандидат остаётся доступен даже при отсутствии профиля в глобальном auth-списке.

Ввод нового текста после выбора сбрасывает подтверждённый выбор, чтобы старый ID не отправлялся под новым поисковым текстом. Смена целевой компании очищает отдел/сотрудника, смена отдела очищает сотрудника. Сервер заново валидирует обе сущности при POST.

Таблица дополнена целевой компанией, целевые отдел и руководитель сохранены. Удаление подтверждается с указанием конкретной компании/отдела. Поля настройки роли, сохранение/очистка role ID, отображение roleSyncStatus и кнопка синхронизации не менялись.

## Проверки

Выполнены sqlc generate, go build ./..., go vet ./..., npm run build и git diff --check в обоих репозиториях. Существующие тесты permission/mysql/vacation запущены дополнительно; они не являются новой проверкой cross-department-сценариев с БД. Новые автоматизированные тесты не писались.

По исходникам прослежены несколько scopes, роль без назначения, удаление одного из нескольких назначений и последнего назначения роли, сохранение самозапрета и административных прав. Фактические HTTP/SQL-операции, доставка уведомлений, миграции и браузерные сценарии не запускались; dev-серверы не поднимались. Сборщик frontend оставляет предупреждение о chunks больше 500 kB — разделение bundle не входит в задачу.

## Ручная проверка в тестовом окружении

Подготовить компании A и B с отделами X/Y, включая одинаковое имя отдела в разных компаниях; руководителя M из компании B/отдела Z; сотрудников S1 из A/X, S2 из B/Y, S3 из неназначенного отдела; второго руководителя N и администратора.

| Сценарий | Ожидается |
|---|---|
| Выбрать A → X → M, работающего в B/Z | M доступен в общем поиске по ФИО; реальное B/Z показано отдельно; создаётся назначение A/X/M. |
| Поиск кандидата без auth-профиля, но с full_name APIREF | Доступен поиск/выбор по APIREF-ФИО, не требуется наличие в usersAll. |
| Начать менять поисковый текст после выбора | Старый ID не отправляется, до нового выбора кнопка недоступна. |
| Несуществующая целевая пара или отсутствующий кандидат через прямой POST | Ошибка до INSERT/выдачи роли. Подмена department на отдел другой company не проходит. |
| Повторить ту же тройку A/X/M | 409, без дубля. |
| Добавить B/Y/M и A/X/N | У M два отдела разных компаний, у A/X два руководителя; все назначения видны с целевыми компаниями. |
| M открывает отпуска S1 и S2, файлы их отпусков | Доступ по назначению и прежним разрешениям, несмотря на собственное B/Z. |
| M открывает отпуск/файлы/табель/историю S3 | Scoped-доступ запрещён. Общая компания или совпавшее название отдела другой компании ничего не добавляют. |
| M подтверждает/снимает табель, исправляет work S1/S2 с причиной | Действуют прежние ревизии, 409, аудит manager и needs_review; кадровые/system-записи защищены. |
| Роль department.manager:manage без строк назначений | Нет доступа к сотрудникам. Само членство M в B/Z не даёт доступ ко всем B/Z. |
| Назначить M ещё и на его собственный отдел | Другие сотрудники этого отдела доступны, сам M исключён из scoped-списков. Собственный отпуск/табель через manager-ветку согласовать нельзя. |
| Администратор с прежними all-правами, без назначений | Прежние утверждение отпусков/табелей и доступ сохраняются, в том числе при ошибке APIREF. |
| Новая pending-заявка S1 | M и N получают уведомление, даже если оба вне A/X; заявитель исключён, admin+manager не получает дубль. |
| Получатель отсутствует или его user_id неоднозначен в APIREF | Уведомление ему не отправляется; scoped-доступ также не выдаётся. |
| Удалить A/X/M, сохранив B/Y/M с тем же authRoleId | Внешняя роль остаётся, следующий запрос к S1 запрещён, к S2 разрешён. N продолжает управлять A/X. |
| Удалить последнее назначение M этой роли | Роль снимается прежним механизмом, scoped-доступ прекращается после успешного удаления. |
| Ошибка снятия последней роли | 503, назначение остаётся и отображает ошибку; повторить удаление после восстановления auth. |
| Перенести M в другой собственный отдел APIREF | Его целевые назначения остаются; к новым коллегам без назначения доступ не появляется. |
| Удалить/перевести S1 в другой отдел APIREF | Следующий запрос использует новое фактическое место работы, старое назначение не предоставляет доступ вне своей пары. |
| APIREF timeout/HTML/не-2xx/пустые/дублированные данные | Нет выдачи scoped-доступа или назначения по умолчанию; нет mock-подстановки в настройки. |
| Старые назначения своего отдела | Работают без переноса данных; обычные сотрудники и прочие разделы не меняют права. |

После завершения работа остановлена; другие задачи не выполнялись.
