# Предварительное согласование отпусков отделом

## Реализованное поведение

Основной `status` сохранён: `pending`, `approved`, `rejected`, `withdrawn`.
Новый независимый `departmentStatus`: `not_required`, `pending`, `approved`, `rejected`.
Исторические заявки получают `not_required`, новые — `pending`.

Полный permission руководителя: `time:department.manager:manage` (с поддержкой существующих wildcard-разрешений permission-сервиса).
Новое разрешение нужно зарегистрировать и выдать руководителям во внешнем permission-сервисе; его данные в этих репозиториях не хранятся.

Помимо permission backend проверяет сессию, оба `user_id`, точное совпадение непустых идентификаторов компании и отдела по действующему upstream-справочнику. Самосогласование запрещено. Повторяющийся `user_id`, отсутствующие идентификаторы и неоднозначный scope не дают доступа. ФИО, названия отделов и frontend mock-данные не используются для авторизации.

Решение руководителя допустимо только при основном и руководительском статусах `pending`. Оно не меняет основной статус, табель и не вызывает финальные уведомления или email. Изменение решения возможно только после нового цикла согласования. Решение и audit-событие записываются в транзакции с `SELECT ... FOR UPDATE` той же заявки, который используется финальным workflow и редактированием.

Любое редактирование заявки, включая смену типа или комментария, сбрасывает действующий этап в `pending` и очищает текущего автора/время/комментарий решения. Старое решение остаётся в истории. Для архивного `not_required` этап не включается. Возврат администратором на рассмотрение также сбрасывает требуемый этап. Отозванные и другие финальные заявки руководитель согласовать не может.

Администратор с `time:vacation.all:edit` сохраняет окончательное утверждение/отклонение независимо от справочника и решения отдела. Финальное утверждение использует прежний workflow с табелем и уведомлениями. Утверждение без положительного решения отдела сохраняет дополнительное событие `department_bypassed`, включая создание сразу утверждённой заявки. Старый контракт финальных PUT-запросов не меняется.

В списке и карточке показаны отдельный статус, автор, время и комментарий руководителя. Кнопки с необязательным комментарием отображаются исключительно при серверном `canDepartmentApprove === true`. Добавлена вкладка «Заявки отдела»; её данные фильтруются на backend. Файлы сохраняют прежние отдельные права доступа, универсальный permission руководителя их не расширяет.

## Настройка и проверка reference API

Серверная авторизация reference API подтверждена пользователем: используется тот же `AUTH_SERVICE_API_KEY`, что и для auth-сервиса, в cookie `session`. Backend берёт токен из существующей env-конфигурации; отдельный reference-токен не требуется. Пустой токен блокирует scoped-операции. Браузерная cookie не пересылается.

В репозиториях найдены frontend-потребители полей `user_id`, `company`, `department`, включая mock fallback. Это не подтверждает однозначность названий отделов. Upstream-реализация и достоверная схема идентификаторов не найдены. Работоспособность интеграции с реальным кадровым сервисом не подтверждена.

Для обращения к справочнику достаточно настроить `APIREF_BASE_URL` и существующий `AUTH_SERVICE_API_KEY`. Дополнительное включение функциональности не требуется: HTTP-ответ и scope проверяются непосредственно при каждом обращении.

Ожидаются строковые непустые `user_id`, `company_id`, `department_id` в каждой записи сотрудника. Поддерживаются плоский JSON-массив записей и массив групп `{ "employees": [...] }`; идентификаторы должны находиться именно в записи сотрудника. Групповые названия не наследуются для авторизации. Список должен содержать внутренних действующих сотрудников.

Отсутствующий сотрудник, повторяющийся `user_id`, пустые идентификаторы компании/отдела и данные только с названиями не предоставляют scoped-доступ. При другой схеме понадобится адаптация парсера под реальный контракт; некорректные данные не дают доступ по умолчанию.

Параметры добавлены в env-конфигурацию и `.env_example`; реальные `.env` и секреты не изменялись:

| Переменная | Назначение |
| --- | --- |
| `APIREF_BASE_URL` | Только origin upstream, например `http://apiref:8080`, без `/apiref`, path, query и credentials в URL. Запрос идёт на `/apiref/ref/employees/internal`, как в frontend-прокси. |
| `AUTH_SERVICE_API_KEY` | Существующий служебный API-токен, общий для auth и reference API; отправляется в cookie `session`. Пустое значение блокирует операции отдела. |

Ранее добавленные `APIREF_AUTH_MODE`, `APIREF_AUTH_HEADER_NAME`, `APIREF_AUTH_HEADER_VALUE` удалены: отдельная настройка механизма авторизации больше не нужна. Реальные `.env` и значения секретов не изменялись.

Клиент имеет таймаут 5 секунд, лимит тела 4 МиБ, запрет redirects и проверку non-2xx. Ошибки конфигурации/HTTP/формата дают `503` для операций отдела; неподтверждённый scope сотрудника — `403`. В существующей выдаче своих/всех заявок сбой справочника только выключает `canDepartmentApprove`; окончательное решение администратора не обращается к reference API.

## Миграция и развёртывание

Новая миграция: `internal/adapter/mysql/migrations/040_vacation_department_approval.sql`, после `039_vacation_workflow.sql`. Добавляет:

- `department_status ENUM(...) NOT NULL DEFAULT 'not_required'`;
- `department_actor_id VARCHAR(36) NOT NULL DEFAULT ''`;
- `department_decided_at TIMESTAMP NULL`;
- `department_comment VARCHAR(4000) NOT NULL DEFAULT ''`.

Старые миграции не менялись. SQL-запросы дополнены, generated-код получен командой `sqlc generate`.

Миграция в рамках реализации **не запускалась**. В проекте pending migrations автоматически выполняются при запуске backend; поэтому запуск новой версии является шагом развёртывания с изменением схемы. Сначала согласовать применение схемы, затем backend, затем frontend. Старые версии при вставке без новых полей сохранят `not_required`; записи, созданные в смешанном развёртывании старой версией, не требуют этапа автоматически.

Для отката достаточно вернуть прежние версии приложений и оставить добавленные колонки: старый код их не читает. Это сохраняет историю и решения. Удаление колонок — отдельная разрушительная операция после вывода нового кода, резервного копирования решений и согласования; автоматического down нет, как и у остальных миграций проекта. Она не выполнялась.

## API

Пути указаны с реальным префиксом backend `/v1`; frontend использует существующий proxy `/apitime`.

- `PUT /v1/vacation/:id/department-decision` — session + `time:department.manager:manage` + серверная scoped-проверка.

  ```json
  { "decision": "approved", "comment": "Согласовано" }
  ```

  `decision`: только `approved` или `rejected`; `comment` необязателен, максимум 4000 символов. Успех `200` с `message`. Ошибки: `400` неверный запрос, `401` отсутствующая сессия, `403` нет permission/scope или самоодобрение, `404` нет заявки, `409` этап завершён/не требуется либо основной статус финальный, `503` справочник недоступен/не настроен/не подтверждён. Проверка permission следует существующему поведению middleware: отказ auth-сервиса даёт `403`.

- `GET /v1/vacation/department/:year` — список только других сотрудников подтверждённого отдела и компании текущего руководителя. Требует тот же универсальный permission. Без reference scope полные заявки не выдаются.
- `GET /v1/vacation/:id` и `GET /v1/vacation/:id/history` — сохранены прежние owner/all права; дополнительно руководитель может читать заявку своего подтверждённого scope. Сам permission не открывает чужие отделы.
- Существующие полные списки и карточка дополнены `departmentStatus`, `departmentActorId`, `departmentDecidedAt`, `departmentComment`, `canDepartmentApprove`. Формат nullable-времени соответствует существующим sqlc DTO: `{ "Time": "...", "Valid": true }` либо `Valid: false`. Автор — `user_id`; frontend показывает доступное ФИО, иначе идентификатор. Урезанный общий календарь не расширяется личными комментариями/решениями.
- Финальные `/approve`, `/status`, редактирование `/application`, `/type`, отзыв `/withdraw` сохраняют прежние контракты.

Новые события существующей истории: `department_approved`, `department_rejected`, `department_reset`, `department_bypassed`.

## Ручной чек-лист

Для позитивных scoped-сценариев настроить реальный upstream по разделу выше. Проверки проводить в согласованном тестовом окружении.

1. Создать новую заявку сотрудника: основной статус `pending`, этап `pending`. Старая заявка после миграции имеет `not_required` и продолжает работать через прежние endpoints.
2. Руководитель с `time:department.manager:manage`, совпадающими company/department IDs: видит заявку во вкладке отдела, карточку/историю и `canDepartmentApprove: true`. Согласование сохраняет автора, время, комментарий и ровно одно событие; основной статус остаётся `pending`.
3. Повторить с отказом руководителя: основной статус остаётся `pending`, этап `rejected`, история содержит комментарий. Табель и финальные уведомления/email до решения администратора не меняются в обоих случаях.
4. Чужой отдел и одинаковое название отдела в другой компании: заявки не входят в scoped-список, чтение карточки/истории через новый доступ и PUT решения запрещены. Проверять без независимого `vacation.all:read`.
5. Отсутствующий permission при совпадающем отделе: прямой PUT и список отдела дают `403`, кнопок нет. Отсутствующая сессия даёт `401`.
6. Собственная заявка руководителя: кнопок нет, прямое решение даёт `403`.
7. Неоднозначный/повторяющийся `user_id`, пустые IDs, данные только с названиями: scoped-доступ не выдаётся. Не применять frontend fallback для подтверждения доступа.
8. Пустой URL, отсутствующий служебный токен, неверная авторизация, non-2xx, redirect, таймаут и неверное/слишком большое тело: отдел не получает доступ. В тех же условиях администратор может окончательно утвердить/отклонить заявку.
9. Последовательный повтор решения: `409`, нет нового события. Два параллельных PUT одной заявки: один успех, второй `409`, одно решение и одно событие.
10. Параллельно выполнить окончательное решение администратора и решение руководителя: финальный статус сохраняет приоритет; если администратор завершил первым, решение руководителя запрещено. После любого финального статуса прямое решение руководителя не проходит.
11. Отозвать pending-заявку: основной `withdrawn`, дальнейшее согласование запрещено. Изменить даты/тип ранее согласованной pending-заявки: этап снова `pending`, поля текущего решения очищены, прежнее решение и сброс видны в истории. Обычное редактирование комментария также сбрасывает этап. Возврат на рассмотрение администратором начинает новый цикл.
12. Утвердить администратором заявки с этапами `pending` и `rejected`: утверждение проходит, в истории есть `department_bypassed` и финальное `approved`, табель/уведомления работают как раньше. Создание сразу утверждённой заявки также фиксирует обход.
13. При положительном согласовании отдела окончательное утверждение создаёт табель только на финальном шаге. При отказе администратора итоговый статус `rejected`, предварительное решение не отменяет его приоритет.
14. Проверить историю: правильные actor IDs, время и комментарии; вне scope без независимого глобального права история недоступна. Файлы продолжают требовать прежних отдельных прав.
15. Проверить существующие вкладки, фильтры, график, расчёт дней и остатка отпуска, а также вход руководителя только с универсальным permission во вкладку отдела и карточку.
