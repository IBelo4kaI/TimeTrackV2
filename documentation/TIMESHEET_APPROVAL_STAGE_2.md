# Подтверждение табелей: этап 2

Реализован только backend. Frontend, расчёты нормы/статистики, кадровые процессы и конфигурация не изменены. Основа и миграции этапа 1 сохранены.

## Права

Проверки сосредоточены в `internal/timeaccess/policy.go`. Идентичность берётся из проверенной сессии auth-сервиса. Отсутствующая идентичность даёт 401. Поля `actor_id`, `actor_type`, `actorId`, `actorType` из JSON не используются.

| Операция | Сотрудник | Руководитель | Администратор |
|---|---|---|---|
| Календарь, статистика, статус и история | Свои, с `calendar:read` | Чужие сотрудники доступного отдела | Любые с `calendar.all:read` |
| Обновление времени | Прежнее `calendar:edit` для себя | Доступный сотрудник, обязательный комментарий | `calendar.all:edit` |
| Создание / удаление времени | Прежние `calendar:create` / `calendar:delete` | Доступный сотрудник, обязательный комментарий | Прежние `calendar.all:create` / `calendar.all:delete` |
| Список табелей | Нет | Сотрудники доступного отдела, без себя | Все сотрудники с `calendar.all:read` |
| Подтверждение / снятие | Нет | Чужие сотрудники доступного отдела | `timesheet.all:approve`, в том числе для собственного табеля |

Для руководителя одновременно нужны `department.manager:manage`, назначение `department_managers` и подтверждённые живым APIREF данные через существующий `DepartmentScopeResolver.Members`. Resolver и правила отделов не заменены. Проверка производится при каждом запросе; принадлежность пользователя frontend не задаёт. Ошибка APIREF даёт 503, отсутствие назначения/однозначного scope или чужой отдел — 403. Полноценные административные права проверяются до scoped-доступа и не зависят от APIREF.

Полные коды прав содержат существующий префикс сервиса, например `time:timesheet.all:approve`. Новое право проверяется действующим permission-клиентом с прежней поддержкой wildcard. Его необходимо выдать соответствующей роли в сервисе авторизации; чтение/редактирование календаря этого права не заменяет. Новые переменные окружения и локальный реестр прав не добавлялись.

Руководитель сохраняет обычную работу с собственным календарём через прежние пользовательские маршруты и права сотрудника. Это не предоставляет самосогласование. Если у руководителя есть отдельное административное право, действует соответствующая административная ветка.

## API

Все маршруты требуют cookie `session`. Ответы новых маршрутов имеют `Cache-Control: no-store`. Месяц — 1–12, год — 1–9999. Невалидный период даёт 400.

| Метод | Маршрут | Результат |
|---|---|---|
| GET | `/v1/timesheets/:year/:month` | Массив доступных сотрудников с состоянием и статистикой |
| GET | `/v1/timesheets/:userId/:year/:month` | Состояние конкретного месяца |
| GET | `/v1/timesheets/:userId/:year/:month/history` | История изменений времени этого сотрудника за месяц |
| POST | `/v1/timesheets/:userId/:year/:month/approve` | Подтвердить месяц |
| POST | `/v1/timesheets/:userId/:year/:month/unapprove` | Снять подтверждение, вернуть `pending` |
| PUT | `/v1/timesheets/:userId/:year/:month/entries` | Создать/обновить/удалить рабочие записи сотрудника |

Состояние: `userId`, `year`, `month`, `status`, `revision`, `approvedRevision`, `approvedBy`, `approvedAt`. Последние три поля nullable; автор — ID пользователя auth-сервиса. Отсутствующая строка состояния читается как `pending`, revision 0. После изменения подтверждённого месяца `needs_review` сохраняет сведения о последнем подтверждении; при явном снятии подтверждения они очищаются.

Список дополнительно содержит только необходимые поля профиля `name`, `surname`, `patronymic`, прежний объект `statistics`, `statisticsUnavailable`, `canEdit`, `canApprove`. `canEdit` соответствует обновлению (`edit`); создание/удаление администратором по-прежнему требуют своих прав. Профили получаются существующим authservice; ответ фильтруется на backend. Сотрудники scope без профиля также остаются в списке по userId. Если пол неизвестен, статистика возвращается как null с `statisticsUnavailable: true`; норма не выдумывается. Сбой authservice или БД не заменяется фиктивной статистикой.

Подтверждение и снятие подтверждения принимают одинаковое тело:

```json
{"expectedRevision": 7}
```

`expectedRevision` обязателен, целое неотрицательное число. Обе операции блокируют строку месяца тем же способом, что и аудируемые изменения времени. Несовпадение ревизии возвращает 409 с `{ "error": "...", "current": { ...состояние месяца... } }`, без изменения подтверждения. После 409 нужно заново загрузить календарь, статистику и статус и проверить актуальные данные. Подтверждается весь месяц, включая месяц без записей. Повтор того же подтверждения уже утверждённой актуальной ревизии сохраняет первоначальные автора/время; после `needs_review` новое подтверждение фиксирует новую ревизию и автора. Административное подтверждение не требует решения руководителя.

Редактирование:

```json
{
  "operation": "update",
  "comment": "Исправлены часы по согласованию с сотрудником",
  "entities": [
    {
      "entryDate": "2026-11-10T00:00:00Z",
      "dayTypeId": "UUID типа work",
      "hoursWorked": "8.00",
      "workLocation": "office"
    }
  ]
}
```

`operation`: `create`, `update`, `delete`; батч непустой, все даты принадлежат месяцу из URL. Для `delete` в entities достаточно `entryDate`. Формат даты соответствует существующим операциям времени (RFC3339), location — office/remote/null. Успех — 204. Новый маршрут предназначен для правки сотрудника руководителем/администратором; обычный сотрудник использует существующие маршруты. На новом маршруте для самостоятельной правки также требуется соответствующее административное право.

Руководителю нужен непустой после trim комментарий до 4000 Unicode-символов. Разрешены создание, изменение и удаление только записей типа `work`, включая изменение часов и места работы. Существующий нерабочий тип нельзя превратить в work, удалить или заменить; новый нерабочий тип тоже запрещён. Дополнительно защищаются существующие записи, у которых в аудите этого userId/даты/entryId есть системный автор либо источник vacation/sick_leave. Проверки выполняются под блокировкой месяца внутри общего аудируемого writer; при отказе весь батч откатывается. Нерабочие записи, существовавшие до аудита, защищены по типу. Историческое происхождение старой work-записи до этапа 1 восстановить по отсутствующему аудиту невозможно.

Контекст manager привязан к проверенным автору и целевому сотруднику. В журнал попадают `actor_type=manager`, реальный actor ID, комментарий и прежние значения до/после. Admin/employee продолжают записываться по прежним правилам. Передача manager/system из тела запроса не меняет контекст.

Старые маршруты `/calendar/:userId/:year/:month`, `/usertimeentries/statistics/:userId/:year/:month/:gender` и `/usertimeentries/create|update|delete` используют ту же политику. Форматы запросов и прежние административные/пользовательские права сохранены. Для scoped-правки через старые create/update/delete добавляется поле `comment` верхнего уровня. Менять кадровые записи через старые маршруты руководителю тоже нельзя. Запись времени выполняется только существующими аудируемыми методами; новых вызовов Raw-методов вне writer нет.

## Миграции и развёртывание

Новых миграций на этапе 2 нет. Нужны 043 и 044 этапа 1, включая защиту истории и FK RESTRICT. Механизм их повторного применения на этом этапе не менялся. Подтверждение и снятие подтверждения не меняют содержимое времени и его ревизию. Реальные изменения автоматически увеличивают ревизию и переводят `approved` в `needs_review`; no-op сохраняет подтверждение.

Порядок: применить основу этапа 1 при остановленных старых пишущих экземплярах, развернуть backend этапа 2, выдать `time:timesheet.all:approve` выбранным административным ролям. Frontend этапа 3 не развёрнут. Откат к предыдущему backend не требует удаления таблиц, истории или назначений; новые API станут недоступны. Откат на backend до аудита вновь допускает неаудируемую запись и требует отдельного решения, поэтому не входит в этот этап.

## Ручная проверка безопасности

В отдельном окружении подготовить обычного сотрудника E, руководителя M, сотрудника его отдела S, сотрудника другого отдела X и администратора A. Руководителю выдать только `department.manager:manage` плюс обычные собственные calendar-права; A выдавать read/edit/approve независимо. Для команд ниже использовать отдельные cookie-сессии и реальные UUID.

```sh
curl -b 'session=MANAGER_SESSION' "$BASE/v1/timesheets/2026/11"
curl -b 'session=MANAGER_SESSION' "$BASE/v1/timesheets/EMPLOYEE_ID/2026/11"
curl -b 'session=MANAGER_SESSION' -H 'Content-Type: application/json' \
  -d '{"expectedRevision":7}' "$BASE/v1/timesheets/EMPLOYEE_ID/2026/11/approve"
curl -b 'session=MANAGER_SESSION' -H 'Content-Type: application/json' \
  -d '{"expectedRevision":7}' "$BASE/v1/timesheets/EMPLOYEE_ID/2026/11/unapprove"
curl -b 'session=MANAGER_SESSION' "$BASE/v1/timesheets/EMPLOYEE_ID/2026/11/history"
curl -b 'session=MANAGER_SESSION' -H 'Content-Type: application/json' -X PUT \
  -d '{"operation":"update","comment":"Уточнение часов","entities":[{"entryDate":"2026-11-10T00:00:00Z","dayTypeId":"WORK_UUID","hoursWorked":"7.00","workLocation":"remote"}]}' \
  "$BASE/v1/timesheets/EMPLOYEE_ID/2026/11/entries"
```

| Сценарий | Ожидается |
|---|---|
| Нет session / auth возвращает пустой user ID | 401, без записи времени/аудита/подтверждения |
| E читает свой статус и историю, календарь/статистику | Доступ по прежним собственным правам |
| E подбирает userId S/X, вызывает список или подтверждение | 403, чужие данные не раскрываются |
| M имеет право, но нет назначения; назначение есть, но нет права | Доступ к отделу запрещён |
| M запрашивает список | Только сотрудники Members, без M; нет профилей/статистики X |
| M читает/правит/подтверждает S | Разрешено; правка с комментарием даёт actor_type manager |
| M подставляет X в каждый новый и старый маршрут, в том числе body userId | 403; нет изменений и чужой истории/календаря/статистики |
| M подтверждает/снимает свой табель | 403; с отдельным timesheet.all:approve разрешено как админу |
| Удалить назначение M или изменить отдел в APIREF между запросами | Следующий запрос S запрещён; старый список не является разрешением |
| APIREF timeout/HTML/не-2xx/дубликат user ID/пустой scope | Scoped-доступ запрещён, без fallback; admin-права сохраняются |
| A имеет только calendar.all:read или edit | Соответствующий доступ сохраняется; подтверждение запрещено |
| A имеет timesheet.all:approve | Подтверждение/снятие любого месяца без руководителя и без APIREF |
| Нет expectedRevision, отрицательное/дробное значение | 400; решение не меняется |
| Изменить время после загрузки revision, затем approve/unapprove со старым значением | 409 с текущим состоянием; подтверждение не записывается |
| Одновременно изменение времени и подтверждение | Сериализация по месяцу: либо 409, либо последующее needs_review |
| Approved, затем реальная правка/удаление времени | Ревизия растёт, needs_review, неизменяемый аудит |
| Approved, затем запись идентичных значений | Ревизия и approved сохраняются, нового события нет |
| Needs_review, подтвердить актуальную ревизию | Approved с актуальной approvedRevision и автором |
| Снять подтверждение актуальной ревизии | Pending, approved-поля null; содержимое и revision неизменны |
| Пустой/пробельный или >4000 символов комментарий M | 400, включая старые маршруты |
| M изменяет/удаляет vacation, medical, decree, time-off либо системную запись | 403; батч целиком откатывается, без изменения revision/истории |
| M создаёт нерабочий тип или заменяет work на medical/vacation | 403, включая старые create/update |
| Батч содержит work и защищённый день | Не изменяется ни один день |
| M отправляет actor_type=admin/system или чужой actor_id | Игнорируются; автор — M, тип manager |
| Батч нового API содержит дату другого месяца | 400, весь запрос без изменений |
| Обычный пользователь создаёт medical-день через прежний календарь | Прежнее поведение сохранено; не требуется страница больничных |

Далее проверить статическую миграционную основу и, только в тестовой БД, сценарии частичного DDL из отчёта этапа 1. Исполнение миграций на живой БД этим этапом не выполнялось.
